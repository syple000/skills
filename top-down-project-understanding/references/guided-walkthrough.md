# 新项目走读模板与示例

本参考用于组织完整的新项目学习回答。它不是固定提纲，而是保证逻辑层、代码映射和验证闭环都不缺失的检查表。

## 推荐的回答顺序

1. **一句话结论**：项目解决什么问题，用户最终得到什么。
2. **项目类型与范围**：本次走读哪条路径，哪些部分暂不展开。
3. **逻辑层模型**：核心对象、输入输出、控制流、数据流、状态和边界。
4. **数据与状态模型**：长期状态、临时状态、粒度、生命周期、不变量。
5. **源码关键路径**：从入口一段段映射，给出文件和符号。
6. **具体样例**：展示一次真实执行中的状态变化。
7. **优化与运行边界**：复杂度、并发、持久化、失败、扩展和限制。

标题可以变化，但顺序通常应保持“逻辑模型先于源码细节”。

## 项目类型对照

| 项目类型 | 先讲什么 | 代码路径重点 | 样例应验证什么 |
|---|---|---|---|
| 算法库 | 输入表示、核心不变量、主循环 | 入口 API -> 预处理 -> 核心算法 -> 结果 | 中间值、终止条件、复杂度 |
| 应用服务 | 请求/事件生命周期、业务状态 | 路由 -> 中间件 -> 业务 -> 存储 -> 响应 | 成功请求、校验失败、状态变化 |
| CLI | 命令意图、配置优先级 | 参数 -> 配置 -> 输入发现 -> 处理 -> 输出 | 命令、产物、退出码、边界输入 |
| SDK/库 | 调用者契约、对象生命周期 | 公开 API -> 内部类型 -> 扩展点 -> 错误 | 典型调用、错误映射、兼容边界 |
| 协议系统 | 参与者、消息、状态机 | 接收 -> 校验 -> 状态转换 -> 发送/持久化 | 消息顺序、超时、重复、恢复 |
| 数据管道 | schema 与数据血缘 | source -> 转换 -> 分区/聚合 -> sink | 一条记录如何逐级变换 |
| 编译器/解释器 | 源语言语义、IR 生命周期 | lex -> parse -> lower -> optimize -> emit | 一段源码经过的各 IR |

不要因为项目含有某种模式就强行加入无关章节。

## 通用逻辑层检查

开场部分至少要回答：

- 系统的外部边界在哪里？
- 最小处理单位是什么，最终产物是什么？
- 一次执行由什么触发，在哪里结束？
- 哪些对象只是中间表示，哪些会长期保留？
- 状态由谁创建、修改、读取和销毁？
- 哪些操作有副作用，事务或一致性边界在哪里？
- 哪些条件会提前返回、重试、回滚或失败？
- 对可逆过程，如何从输出恢复输入或解释输出？

如果这些答案仍依赖代码才能理解，说明逻辑层还不够独立。

## 代码映射写法

不要只列函数。对每一段关键路径说明四件事：

```text
输入是什么
这里做了什么决定或变换
持有哪些状态，谁修改它
输出交给谁，或产生什么副作用
```

源码引用保持少而精确。一个位置支撑一个关键判断，不要把整份源码抄进回答。

### 控制流笔记

```text
trigger
  -> validation
  -> important branches
  -> core operation
  -> persistence / response
  -> cleanup / recovery
```

### 数据流笔记

```text
external input
  -> normalized representation
  -> domain object
  -> transformed state
  -> output / storage
```

两者不一致时，明确解释。例如请求可能先返回、后台任务稍后持久化，或者一个输入被拆给多个并发消费者。

## 样例走查模板

选择一个能暴露核心机制的例子：

```text
输入：
初始状态：

步骤 1：谁做了什么 -> 状态变化
步骤 2：谁做了什么 -> 状态变化
步骤 3：终止条件 -> 输出
```

对于算法，显示真实数值；对于服务，显示请求作用到的对象和持久状态；对于 CLI，显示参数如何变成文件操作；对于数据管道，显示一条记录在各阶段的 schema。

随后验证：

- 主路径是否与代码一致；
- 一个错误、空值、超时或边界值如何处理；
- 如果过程可逆，输出能否按代码中的逆过程恢复；
- 如果存在缓存或增量状态，起点与冷启动是否等价。

## 运行边界检查

用户理解主流程后，再按项目类型选择相关内容：

- 时间、空间、I/O 和网络复杂度；
- 最大数据量由哪一步决定；
- 全量加载、流式处理、外部排序或磁盘持久化；
- 锁、并发、竞态、事务、幂等和重试；
- 配置变更、兼容性、迁移和持久化格式；
- 可观测性、错误恢复、测试覆盖与明确不支持的能力。

不要把“架构上可以扩展”说成“当前实现已经支持”。

## 示例一：可逆算法（BPE，仅作示例）

这是从一个项目中抽象出的局部例子，用来展示“先逻辑、后实现”的粒度；其他项目按自身结构替换。

逻辑层可以这样开场：

```text
初始单位：256 个 byte token
处理边界：文本先切成独立 chunk
训练循环：统计相邻 pair -> 选最高频 -> 生成新 token -> 替换 -> 重复
编码：按已学 merge 的优先级重放合并规则
解码：从基础 token 和 merge 关系重建字节，再还原文本
```

小规模训练：

```text
语料：abab x 2，abc x 1
初始：
  abab -> [97, 98, 97, 98]
  abc  -> [97, 98, 99]

pair：
  (97, 98): 5
  (98, 97): 2
  (98, 99): 1

merge：
  (97, 98)   -> 256
  (256, 256) -> 257
  (256, 99)  -> 258
```

编码 `ababc`：

```text
[97, 98, 97, 98, 99]
-> [256, 97, 98, 99]
-> [256, 256, 99]
-> [257, 99]
```

解码 `[257, 99]`：

```text
256 = ab
257 = ab + ab = abab
257, 99 -> ababc
```

进入源码后，再把“预切分、pair 统计、merge 选择、状态更新、encode、decode”分别映射到真实结构和函数。这个示例只说明可逆算法的讲法，不定义 skill 的范围。

## 示例二：请求型服务（抽象）

逻辑层先说明：

```text
HTTP request
  -> parse and validate
  -> load aggregate from store
  -> apply business transition
  -> persist transaction
  -> return response or enqueue follow-up
```

样例展示一个请求如何改变对象状态，并检查校验失败、事务回滚或后台重试。进入源码时，再分别映射路由、中间件、业务函数、repository 和事务边界。

## 最终自检

- 如果遮住所有文件路径，用户是否仍能用自己的话复述系统主流程？
- 每个核心术语是否有明确粒度和生命周期？
- 代码路径是否回答了“怎么做到”，而不只是“这里有什么”？
- 具体样例是否真的运行了项目逻辑，而非泛泛比喻？
- 最后是否把算法要求与当前实现限制分开？
